# 构建与元数据

SuperKernel 应用启动时不会发现它的类。`skernel build` 一次性发现它们，并把发现的结果写成元数据；应用在启动时恢复这些元数据。本指南说明构建写出什么、何时必须重新运行，以及缺失或过期的构建如何报告。[文档索引](../README.zh-CN.md)

## 为什么应用启动时不扫描

发现服务意味着加载每个已安装包的每个类并读取其注解。如果每次启动都这样做，启动会变慢，会加载应用从不使用的代码，并使打包后的应用依赖于能够扫描的源码。因此这项工作被拆开：

- `skernel build` 在独立的 PHP 进程中加载项目的类，收集它们的注解，并写出结果。
- 启动时，`super-kernel/metadata` 恢复包元数据，`super-kernel/annotator` 恢复注解记录，`super-kernel/di` 用它们构建容器。恢复只读取生成的文件并对 `composer.lock` 计算哈希：它从不扫描源码、解析 Composer 文件或启动进程，因此项目移动之后以及在打包后的应用中同样能工作。

代价是元数据必须与代码一致。`skernel run` 和 `skernel package` 在运行或归档之前都会先构建，因此只有在你自己启动 PHP 入口时才需要考虑这个问题。

## `skernel build` 生成什么

`skernel build` 作用于当前目录或 `-d` 指定目录中的项目，该项目必须已安装依赖，包括 `super-kernel/metadata`、`super-kernel/context` 和 `super-kernel/di`。它先重新生成项目的 Composer 自动加载器，使上次构建之后添加的类能够被找到，然后在托管 PHP 的两个独立进程中运行：

1. 第一个进程加载项目自己的自动加载器，检查已安装的 `super-kernel/metadata` 的构建协议，映射每个已安装包的类，收集声明了注解的类的注解，并通过项目自己的 `super-kernel/metadata` 和 `super-kernel/annotator` 发布这些记录。
2. 第二个进程用这些记录创建容器，并发布 `SuperKernel\Event\ApplicationBuild`，使各组件写出它们在构建时准备的内容，例如 `super-kernel/aop` 的代理。它不会创建或运行应用。

所有内容都写在依赖目录（vendor 目录）下，并遵循 Composer 的 `config.vendor-dir`：

| 文件 | 内容 |
| --- | --- |
| `vendor/.cache/build.json` | 构建标记：构建协议、SKERNEL 版本、`composer.lock` 的 SHA-256，以及项目目录相对于依赖目录的路径。 |
| `vendor/.cache/metadata.ser` | 每个已安装的包及其类映射。 |
| `vendor/.cache/packages.ser` | 注解记录的索引：每个包及其已安装的引用。 |
| `vendor/.cache/annotations/<vendor>/<package>.ser` | 一个包的注解记录。 |
| `vendor/.cache/mimic/` | 项目声明了切面时，`super-kernel/aop` 准备的代理。 |

构建标记形如：

```json
{
    "protocol": 1,
    "skernel": "1.0.0-alpha.2",
    "lock": "ee15a742b47d0086ea577b57ea8a06b72e7a54a11564a449ac560c7c2a439961",
    "base-path": ".."
}
```

这些文件是派生数据：不要把它们纳入版本控制，随应用一起发布，并让 `skernel build` 重写它们。`skernel package` 会为它写出的包构建一份新的副本，`skernel clean` 会删除它们。构建进程打印的所有内容都输出到 STDERR；成功时 STDOUT 只有一行：

```text
Build artifacts written to /path/to/my-app/vendor/.cache.
```

## 何时需要重新构建

在以下情况下，请重新运行 `skernel build`，或者使用会先构建的 `skernel run`：

- `composer install` 或 `composer update` 之后；
- 修改 `composer.json` 中的自动加载规则之后；
- 添加、删除或修改带注解的类，或者修改注解本身之后；
- 在包含与不包含开发依赖的安装之间切换之后。

应用只能检测到其中一部分。启动时，它把构建标记中的协议与已安装的 `super-kernel/metadata` 比较，并把标记中的哈希与当前的 `composer.lock` 比较。修改类、修改自动加载规则，或者在 `composer install` 与 `composer install --no-dev` 之间切换而 `composer.lock` 没有变化，都不会被检测到：应用会使用旧的元数据运行，因此新的服务、监听器或路由只是不存在。

添加类只需要下一次构建：构建在加载项目的类之前会重新生成 Composer 的自动加载器，因此即使 skeleton 让 Composer 的类映射成为权威（authoritative）映射，新类也会被包含。

## 缺失或过期的构建

当生成的文件缺失、无效或与安装不一致时，恢复容器会抛出 `SuperKernel\Metadata\Exception\BuildRequiredException`。它的消息说明问题，并且总是以 ``Run `skernel build` to generate the project metadata.`` 结尾：

| 问题 | 消息 |
| --- | --- |
| 没有构建标记 | ``The build stamp <vendor>/.cache/build.json is missing. Run `skernel build` to generate the project metadata.`` |
| 无法读取构建标记 | ``The build stamp is invalid. Run `skernel build` to generate the project metadata.`` 或 ``The build stamp has an unexpected structure. Run `skernel build` to generate the project metadata.`` |
| 构建标记是按另一个构建协议写出的 | ``The metadata was generated by SKERNEL <version> under build protocol <n>, but this project expects <n>. Run `skernel build` to generate the project metadata.`` |
| 没有 `composer.lock` | ``The project <directory> has no readable composer.lock. Run `skernel build` to generate the project metadata.`` |
| 构建之后 `composer.lock` 发生了变化 | ``The metadata generated by SKERNEL <version> does not match the current composer.lock. Run `skernel build` to generate the project metadata.`` |
| 包元数据缺失或损坏 | ``The package records <vendor>/.cache/metadata.ser are missing. Run `skernel build` to generate the project metadata.``、``The package records are invalid. …`` 或 ``The package records cannot be restored. …`` |
| 注解记录缺失、损坏或属于其他包版本 | ``The generated annotation records cannot be restored. Run `skernel build` to generate the project metadata.``，`super-kernel/annotator` 给出的原因作为其前一个异常（previous） |

应用入口通过 `SuperKernel\Context\ApplicationContext::getContainer()` 获取容器，它把失败报告为 `SuperKernel\Context\Exception\ContainerInitializationException`，并以 `BuildRequiredException` 作为其前一个异常。没有构建就启动时，skeleton 的入口会以一个未捕获的异常结束，其开头几行是：

```text
PHP Fatal error:  Uncaught SuperKernel\Metadata\Exception\BuildRequiredException: The build stamp /path/to/my-app/vendor/.cache/build.json is missing. Run `skernel build` to generate the project metadata. in …
Next SuperKernel\Context\Exception\ContainerInitializationException: Unable to initialize the application container through SuperKernel\Di\Provider\ContainerProvider. in …
```

## 被跳过的类

构建会跳过它无法加载或者无法创建其注解的类，即使加载该类会以致命错误结束进程也是如此。各进程结束之后，它在 STDERR 上列出被跳过的类，每行一个，按包和类排序，并附上错误类型和消息：

```text
SKERNEL skipped 2 classes whose attributes could not be collected:
  acme/app App\Broken\Listener: Error: Class "App\Missing" not found
  acme/app App\Broken\Proxy: fatal error: Declaration of App\Broken\Proxy::run() must be compatible with ...
```

构建仍然成功，但被跳过的类没有元数据：对应用来说，它的服务映射、监听器、路由或其他注解都不存在。请修复该类并重新构建。新 skeleton 项目中的列表会列出依赖未安装的可选 Symfony 集成中的类，例如 `Symfony\Component\Console\ConsoleBundle`；这些可以忽略。

应用启动时不会打印这个列表。记录中保存了它：容器中的 `SuperKernel\Contract\AnnotationCollectorInterface` 同时实现了 `SuperKernel\Contract\ScanDiagnosticsInterface`，其 `getDiagnostics()` 为每个被跳过的类返回一行，字段为 `sequence`、`package`、`class`、`exception_type` 和 `message`。

## 构建协议

生成文件的格式有一个版本号，即构建协议，由已安装的 `super-kernel/metadata` 以 `SuperKernel\Metadata\Constants\Protocol::VERSION` 声明。每个 SKERNEL 发布版生成一种协议。在写出任何内容之前，`skernel build` 会比较两者，并以一条说明应升级哪一方的消息停止：

| 情形 | 消息 |
| --- | --- |
| 项目的包比 SKERNEL 新 | `The project's super-kernel/metadata uses build protocol <n>, but this SKERNEL generates protocol <n>. Upgrade SKERNEL, for example with "skernel self-update".` |
| SKERNEL 比项目的包新 | `The project's super-kernel/metadata uses build protocol <n>, but this SKERNEL generates protocol <n>. Upgrade the project's SuperKernel packages, or use a SKERNEL release that generates protocol <n>.` |
| 项目没有安装 `super-kernel/metadata` | `The project does not install super-kernel/metadata, so SKERNEL cannot publish its build artifacts. Require SuperKernel 1.0.0-alpha.2 or later.` |

该消息打印在 STDERR 上，`skernel build` 以状态码 1 退出。启动时，应用以同样的方式检查构建标记中的协议，不一致时抛出上面列出的 `BuildRequiredException`。

## 移动和打包已构建的项目

生成的文件保存的是相对于项目目录和依赖目录的路径。当依赖目录位于项目内部时，项目可以连同它的构建一起移动并保持有效；位于项目外部的依赖目录会被记录为绝对路径。在打包后的应用中，路径以 `phar://` 开头，同样的恢复也能工作。`skernel package` 会安装、构建并归档一个临时副本，因此包中携带的构建总是与它的代码一致。
